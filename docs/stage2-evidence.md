# 阶段二实测证据（M1 ~ M8）

所有数字都来自本机真实调用。原始 JSON 由脚本写入 `reports/`（已被 `.gitignore` 忽略，
它是运行产物），随时可以重跑生成。

**版本锚定**：仓库已 `git init`，下面每一份报告都来自**干净工作区**：
`code_version = 228b263`、`is_reproducible = true`、`git describe --tags --dirty = v0.3.0`。
M3 的离线证据锚定在 tag `v0.5.0`（真实模型的三方对比要花钱，放在 M3.1 重跑，见第 9 节）。
M4 的故障注入与并发压测锚定在 tag `v0.6.0`（`code_version = 1fd5135`），见第 11 节。

> `is_reproducible=true` 只保证**输入**可复现（代码版本 + prompt + 模型 + 用例集全部钉死），
> **不保证输出可复现**：同一个 manifest 的两次真实运行分数就不一样（7.2 节）；编排层自己
> 出过一次「数字对不上」的 bug（7.3 节）；供应商也不是恒速的（7.4 节）。

## 0. 端点事实（先搞清楚的坑）

| 事实 | 观测值 | 影响 |
| --- | --- | --- |
| 请求模型 vs 实际返回 | 请求 `deepseek-chat` → 返回 `deepseek-flash` | 供应商会做别名解析，trace 必须同时记 `requested_model` 与 `model` |
| 可用模型名 | `deepseek-flash`、`deepseek-v4-pro` | 官方价目页已确认：以**人民币元**计价，空闲时段为高峰价的一半 |

| 健康窗口延迟 | 0.4 ~ 2.4 s（单条，串行） | 这就是 B 档真模型压测的基线量级 |
| **拥塞窗口延迟** | 同一端点、同一 Key，实测 **12.9 ~ 28.8 s/次**，并出现超时回退 | 版本对比必须在健康窗口内做，见 7.4 |

## 4. 成本口径（不要跳过的坑）

| 场景 | 行为 |
| --- | --- |
| 模型有内置价目（`deepseek-flash` / `deepseek-v4-pro`） | 直接算出**真实成本**，`cost_is_complete=true` |
| 模型无价目 | 记 0 成本但标记 `cost_is_complete=false`，报告里声明「成本只算下限」 |
| 设置了 `AGENTEVALOPS_BUDGET` | 无价目时**直接报错**（`UnknownModelPriceError`），因为上限形同虚设 |
| 价目表里混了美元条目 | 账本直接报错，拒绝把元和美元加总 |

**165 条报告的成本怎么复核**（这一条差点被误判成记账 bug）：

| 项 | 计算 |
| --- | --- |
| 缓存未命中输入 | 17803 tokens × 2 元 = 35606 |
| 缓存命中输入 | 2432 tokens × 0.04 元 = 97.28 |
| 输出 | 2442 tokens × 8 元 = 19536 |
| 合计 | (35606 + 97.28 + 19536) ÷ 1e6 = **CNY 0.055239** ✓ |

只按「输入全价」反推会得到 0.060006 元，于是看起来「账本算错了」。**缓存命中折扣是
承重的**：同一段 system prompt 在 159 次调用里重复出现，命中部分按 1/50 的价格计费。

### 6.1 为什么是「159 次调用 / 165 条用例」

用例矩阵里有 6 条畸形请求，它们在 `handle()` 里、调用规划器**之前**就被请求级校验拒绝，
因此**根本不产生模型调用**：

| case_id | 消息 | customer_id | 结果 |
| --- | --- | --- | --- |
| `v2_bnd_whitespace_only` | 5 个空格 | CUST-001 | `validation_failed` |
| `v2_bnd_tab_only` | 两个制表符 | CUST-001 | `validation_failed` |
| `v2_err_validation_04` | 空字符串 | CUST-001 | `validation_failed` |
| `v2_err_validation_05` | 3 个空格 | CUST-001 | `validation_failed` |
| `v2_err_validation_06` | 正常消息 | 空字符串 | `validation_failed` |
| `v2_err_validation_07` | 正常消息 | 3 个空格 | `validation_failed` |

所以报告把它们单独记成 `source=not-planned`（`source_breakdown = {llm: 159, not-planned: 6}`），
并用三项不变式自检（见 7.3）：每次调用必落在高峰/空闲之一档、模型调用数不超过进入规划层的
用例数、所有短路用例状态都是 `validation_failed`。

### 6.2 9 条差异的归类

**9 条差异全部落在规格灰区，没有一条是「模型明确犯错」**：

| 类别 | 条数 | 说明 |
| --- | --- | --- |
| A：期望值编码了 v1 的正则边界缺陷 | 3 | 中文/数字紧贴订单号时 v1 认不出，v2 正确抽出 → **v2 更好** |
| B：意图粒度未定义 | 4 | 「意图明确但缺订单号」：v1 判 `no_action`，v2 判查单后报缺参数 |
| C：安全语义未定义 | 2 | 两者都无越权副作用，差别只在状态名 |
| **真正的 v2 错误** | **0** | — |

逐条归类与根因见 `docs/bad-cases-v2.md`。

**这条结论比分数本身重要**：上面这些期望值是从 v1 的**实现**导出的，所以它度量的是
「与基线的差异」，不是「正确性」。因此在 2026-10-15 冻结了规格 `docs/agent-spec.md` v1.0，
把 9 条差异逐条裁决：

| 裁决 | 条数 | 依据 | 后果 |
| --- | --- | --- | --- |
| **v2 正确** | 7 | v1 违反 SPEC-SLOT-1（订单号边界）/ SPEC-INTENT-2（缺槽位不改意图） | 期望值按规格改写，v1 的违反登记为基线偏差 |
| **v1 正确** | 2 | v2 偏离 SPEC-INTENT-3（越权请求仍按业务动作判意图） | 期望值不变；v2 的偏离无安全后果，属模型侧待修 |

因此**本文 6 节表格里的分数是冻结前的旧口径**；冻结后重跑见 6.3。

| 状态准确率 | 95.8% | **98.8%** | **+3.0%** |

用量：prompt 20235 / completion 2412 tokens；平均延迟 **768 ms**；花费 `CNY 0.054999`；

差异集合仍是同样那 9 条，但**归属翻转了**：其中 7 条是 **v1 违反规格**（SPEC-SLOT-1 三条、

为了让「干净」这个状态能维持住，做了两件必要的事：

1. **`reports/` 改成 `.gitignore`。** 报告每次运行都会重写（含时间戳），一旦入库，
   工作区就永远是脏的，于是下一次运行的 `code_version` 会带 `-dirty`、
   `is_reproducible` 恒为 `false`——版本对比永远锚不住。结论留在 `docs/`，原始报告交给 CI 当工件。
2. **跑对比前先检查工作区。** `compare_planners.py` 在花钱调用模型**之前**就会告警：
   非 git 仓库（`nogit`）或脏树（`xxx-dirty`）都意味着本次结果不能当锚点。

### 7.2 同一个版本跑三次，分数不一样

同一个 `manifest_id`（`4d598346aff3`）、同一份 prompt、`temperature=0`，165 条用例跑了三次：

| 采样 | 意图准确率 | 与 v1 的差异条数 | 平均延迟 | completion tokens |
| --- | --- | --- | --- | --- |
| run1（锚定前） | 96.4% | 9 | 917.2 ms | 2427 |
| run2 | 95.8% | **10** | 704.6 ms | 2445 |
| run3 | 96.4% | 9 | 723.2 ms | 2427 |

多出来的那一条是 `v2_err_unsupported_04`（「订单 ORD-1001 多少钱」）：run2 里 v2 判成
`order_status` 跑去查单，run1/run3 判 `unknown` 拒绝。也就是 **9 条稳定差异 + 1 条偶发差异**。
这是**供应商侧的采样随机性，不是我们代码的**。

2026-10-15 在 `v0.2.0` 上重跑第四次：意图 96.4%、9 条差异、平均延迟 852 ms、
completion 2442 tokens——与 run1/run3 一致，说明这 9 条是稳定差异（口径是冻结前的期望值）。

**结论（最容易踩的坑）**：

- `manifest_id` 标识的是**版本**，不是**输出**。两次运行 manifest 完全相同，分数却差了 0.6 个百分点。
  所以版本对比**必须报告重复执行的方差**，否则会把模型抖动当成版本退化去查半天。
- 单次 165 条的噪声水平约为 ±1 条用例。要判断「v2 是否真的退化」，
  每个版本必须重复跑 N 次取均值/多数票（已列入待办）。

### 7.3 编排层的一次真实 bug：165 条用例只统计出 159 次调用

重跑 165 条时报告出现了两个对不上的数字：`cases=165` 但 `peak_calls=159`（少了 6 次），
而成本 `0.055127` 元按高峰价反推也对不上。第一反应是计价记账写错了，**实际不是**：

| 排查步骤 | 结论 |
| --- | --- |
| 用可控时钟单独记录 165 次调用 | `calls=165`、`peak+off=165`，记账代码正确 |
| 按 `缓存未命中×2 + 缓存命中×0.04 + 输出×8` 重新核算 | 恰好等于 `0.055127` 元，**成本是对的** |
| 统计每行 `v2_source` 与延迟 | 165 行全是 `llm`、延迟全非零 —— 但内层客户端只被调用了 **159** 次 |

根因是两个 bug 叠在一起：

1. **`handle()` 没清空 `last_plan`。** 6 条畸形请求在规划前被拒绝，报告却读到了**上一条用例**
   的 `last_plan`，于是把它们记成 `source=llm`，延迟也显示成上一条的。
2. **离线自检的脚本答案错位。** `offline_scripts()` 给全部 165 条都发了答案，但只有 159 条
   会真正调用模型；脚本客户端是**按调用顺序**回放的，多发的 6 条让后面每条答案整体错位，
   于是「v2 必须与 v1 完全一致」的自检**虚报了 58 条差异**。

修复（提交 `e95ce18`）：

- `agent.handle()` 入口先 `self.last_plan = None`；抽出 `pre_plan_rejection()` 让 agent 与
  编排层共用同一份判定，两边规则不可能再不一致；
- `offline_scripts()` 只给会进入规划层的用例发答案；

### 7.4 供应商拥塞窗口：同一份用例，延迟差 30 倍

| 观测 | 健康窗口 | 拥塞窗口 |
| --- | --- | --- |

- 版本对比**必须在健康窗口内做**，并且要在结论里记录当时的延迟量级；

### 9.4 已知检索缺口（**没有**写进用例集）

下面这些提问按语义「应该」检索得到，但现在仍是 `hits = []`。它们不被写成用例，
因为把缺陷写成期望值，等于把缺陷固化成规格（SPEC-JUDGE-2 明令禁止）：

- `退货运费政策是怎么规定的`、`退货要多久`
- `发票怎么开`、`运费怎么算`
- `会员的等级划分规定是什么`
- `退款以后优惠券会退回吗，旧版是怎么规定的`

另一侧是召回噪声：`分期免息的费用标准` 会命中改地址条款，`环保回收的补贴标准` 会命中运费条款；
也就是说，「费用 / 政策 / 规定」这类高频低区分度词的组合仍能越过 0.34 阈值。

> 这两个方向是同一个旋钮的两端：阈值调低噪声更多，调高召回更缺。修它需要**评测驱动的调参**
> （拿这 48 条检索用例当目标函数），而不是再手调一次常数。留给 M3.1。

   模型把「缺槽位的退款请求」判成了 `policy_qa`，而确定性检索门没放行（不走 `retrieve`），

   而不是期望的「缺订单号」。这是**确定性门与模型意图互相矛盾**时的行为，M4 要定规格。
2. **没有延迟 / 吞吐证据**：这里全是顺序调用，没有并发；P95、吞吐、错误率留给 M4 压测。
3. **每个配置只跑一次**：见 §10.4，噪声比结论大，所以下面的说法只算方向性 ——
   v3 模型臂（99.2%）略低于 v3 规则臂（100%）；v2（100%）在主矩阵上不低于 v3（99.5%）。
4. **检索缺口仍在**（§9.4）：这批用例没有覆盖那 6 条召回缺失的提问，所以 99.2%
   说的是**当前用例集**下的表现，不是「检索层已经完备」。

## 11. 证据七：M4 故障注入与并发压测（tag `v0.6.0`）

前六份证据都在回答「正常路径对不对」。这一节回答两个新问题：**坏的时候会不会更坏**，
和**并发上来以后还好不好**。两者都不花一分钱——故障注入是进程内的脚手架，压测走的
是建模延迟。

```powershell
D:\Python\python.exe scripts/run_faults.py
D:\Python\python.exe scripts/load_test.py --users 50 --spawn-rate 10 --run-time 20s
D:\Python\python.exe scripts/load_test.py --arm rules --users 20 --spawn-rate 5 --run-time 15s --port 8131
```

### 11.1 故障注入：25/25 通过，而且注入**确实发生了**

规格先冻结了 6 条（SPEC-FAULT-1..6，`docs/agent-spec.md` §2.11 / §7.3），用例再照着写。
报告 `reports/fault-run-20261015T152419+0000-spec1.3.json`（规格 1.3 / 代码 1fd5135）：

| 类别 | 通过 | 总数 |
| --- | --- | --- |
| `fault_timeout`（工具超时 / 检索超时） | 7 | 7 |
| `fault_unavailable`（工具 5xx / 检索 5xx） | 6 | 6 |
| `fault_empty_retrieval`（注入式空检索） | 6 | 6 |
| `fault_rate_limit`（模型限流 → 降级） | 6 | 6 |
| **合计** | **25** | **25** |

- 注入计数 `{tool:timeout 6, tool:unavailable 5, retrieval:empty 6, retrieval:timeout 1, retrieval:unavailable 1, model:rate_limit 6}`
- 限流被计数的调用次数 `rate_limited_calls = 7`（比 `model:rate_limit` 的 6 多 1，因为有一条用例在两轮里各撞了一次）
- 错误码分布 `TOOL_TIMEOUT 7 / TOOL_UNAVAILABLE 6 / NO_KNOWLEDGE 5 / UNSUPPORTED_INTENT 1`
- 用例集指纹 `fa390b4dfb9c623269115ca5b48ca0e7e3ce61c73d6a323d01fc2da611edc54c`

**注入计数是这份报告里最要紧的字段**，不是通过率。没有它，「25 条全过」有两种解释：
Agent 处理得对，或者故障压根没生效——二者在通过率上完全同形。所以 `FaultyTool` 每次
真的抛错都要在自己身上记一笔，报告再把这一笔记出来对账。

三条口径是这一轮**新冻结**的，都不是顺手写的：

1. **写操作不得重试**（SPEC-FAULT-2）。超时那一刻无法判断对方是否已受理，重试退款
   等于可能退两次。所以超时的期望终态是 `tool_failed`，不是「重试后成功」。
2. **5xx 与超时分开计数**（SPEC-FAULT-3）。「对面挂了」和「对面可能还在做事」处置方式
   不同，混成一个数字就没法做告警。
3. **注入的空检索必须与「知识库真没有」行为逐字段一致**（SPEC-FAULT-5）。否则这条用例
   测的是注入器，不是 Agent。

### 11.2 并发压测：P95 / 吞吐 / 单次成功任务成本

服务端是 `src/agentevalops/service.py`（把 v3 链路包成 HTTP），压测客户端在 `perf/`。
tag `v0.6.0` 上的三次运行：

| 报告 | 模型臂 | users | 请求 | RPS | P50 / P95 / P99 (ms) | 服务端自报延迟均值 | http 错误率 | 任务成功率 | 单次成功任务成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `...T152434Z` | `modeled` | 50 | 2315 | 129.8 | 340 / 550 / 720 | 76.9 ms | 0.000% | 100.000% | CNY 0.00076 |
| `...T152525Z` | `rules` | 20 | 2217 | 179.2 | 94 / 130 / 190 | 4.3 ms | 0.000% | 100.000% | CNY 0 |
| `...T152651Z` | `rules` | 20 | 2890 | 210.1 | 88 / 100 / 140 | 3.7 ms | 0.000% | 100.000% | CNY 0 |

**这些数字全是 mock 臂的，报告第一眼就写明了**：`provenance = {"latency": "modeled",
"tokens": "modeled"}`。`LatencyLLMClient` 一个字节都不发网络，60ms 是 `time.sleep`、
token 是固定估计值（260 + 30），只是借 `deepseek-flash` 的价目折算出一个可比较的成本量级。
它证明的是「**服务端**在这套配置下扛得住 50 并发、不丢请求」，**不是**「DeepSeek 的产能
或报价」。真实的 P95 和真实账单只有 `scripts/load_test.py --real` 一条路，而它会花钱。

两点可以拿来交叉验证的口径：

- `modeled` 臂的服务端自报延迟均值 76.9ms，比 `rules` 臂的 4.3ms 高 72.6ms，量级正好落在
  注入的 60ms 假延迟上（多出来的部分是线程池排队）。**建模的那一跳按预期出现在了它该出现
  的位置**，说明压测确实在压链路，而不是压了个空壳。
- `modeled` 臂的 `locust P50 (340ms)` 与 `服务端自报延迟 (76.9ms)` 差 263ms，`rules` 臂差
  84ms。这一段是排队 + 客户端开销。两台进程（locust 与 uvicorn）跑在**同一台机器**上抢
  同一个 CPU，所以本机量出来的 P95 里含客户端自己的调度开销，**不能读成纯服务端延迟**。
  要拆开这一块，得让压测机与被测机分开——目前没有第二台机器。

**最重要的一个观察是方差，不是任何单个数字。** 同一份配置（`--arm rules --users 20
--spawn-rate 5 --run-time 15s`）在本机跑了三次：RPS `125.4 / 179.2 / 210.1`，P95
`220 / 130 / 100` ms。RPS 差 1.7 倍、P95 差 2.2 倍，代码一个字都没改。这和 §10.4 的结论
是同一件事：**单次运行的性能数字不能用来比较两个版本**，要压版本间的差异必须先压方差
（`--repeat N`，M5）。

### 11.3 一个口径 bug：业务终态不能计进错误率

压测脚本的第一版把**业务终态**也算成了错误，于是 `error_rate` 报出 7.27%。那 7.27% 里
绝大部分是两样东西：

- 拒答（`no_action` + `NO_KNOWLEDGE`）：知识库里没有就该拒答，**这是正确行为**；
- 重复退款（`REFUND_NOT_ALLOWED`）：`RefundTool` 对同一 `(order_id, customer_id)` 幂等，
  第二次起返回同一个 REF 号，同样正确。

把这些算成错误，等于说「系统越守规矩，错误率越高」。如果这个数字进了 CI 门禁，那么
**Agent 越守规格，构建越红**——门禁会逼着人把规格改坏。

改法是拆成两个各自有明确语义的指标：

| 指标 | 门禁 | 判的是什么 |
| --- | --- | --- |
| `http_error_rate` | ≤ 1% | **传输层**：非 200、连接异常、超时、响应不是 JSON |
| `task_success_rate` | ≥ 99% | 这一轮的终态是不是**这条消息该有的结果**（期望表在 `perf/locustfile.py` 顶部） |

顺带一个同源的小 bug：请求数对账原本用的是**绝对值**宽容度（差 ≤ 5 次），到了
200+ RPS 就会假警报——2217 次里差 6 次是 0.27%，成本上完全不可见，却打出「口径存疑」。
已改成绝对值与 0.5% 取大（`inflight_tolerance()`）。**一个会经常误报的告警，等于没有告警**，
它只是训练人忽略它。

### 11.4 还没能证明的事

1. **真实 P95 / 吞吐 / 成本仍是空白**。上面每一个延迟与 token 都是建模值。`--real` 会花
   真钱，且供应商有拥塞窗口（§7.4），需要在低并发下先跑一轮拿真实基线。
2. **只有单进程**。`/metrics` 是进程内计数，`uvicorn --workers N` 会让每个进程各有一份，
   脚本必须逐进程聚合；当前按单进程多线程跑（anyio 线程池默认 40 线程，那也是并发的真实
   上界）。多进程的聚合没做。
3. **两进程同机**，所以延迟里混了客户端自身的调度开销（§11.2）。
4. **故障与压测还没合流**：25 条故障用例是顺序跑的，没有在并发下重跑过。降级路径
   （`llm-fallback`）在限流风暴下的表现、写操作在超时下的幂等，都只验证了单请求语义。

## 12. 证据八：CI 回归门禁与发布冻结（tag `v0.7.0`）

到 §11 为止，每一份证据都是**一次**运行的快照。它们回答不了「这一版比上一版好还是坏」，
因为 `reports/` 被 gitignore 掉了——上一版长什么样，没有地方记得。

这一节补的就是那个比较对象，以及拿它做判断的判据表。

### 12.1 冻结：把「这一版长什么样」写进 git

```powershell
D:\Python\python.exe scripts/freeze_release.py
```

五项检查全离线、零成本，跑完写进 `releases/v0.7.0/`：`release.json`（机器读的指标索引）、
`README.md`（同一份内容的人读版），加上五项检查各自的原始报告。

| 检查 | 耗时 | 结果 |
| --- | --- | --- |
| `pytest` | 35.6s | 1061 passed / 0 failed（另有 10 xfailed） |
| `faults` | 7.7s | 25/25 |
| `comparison:matrix`（213 行） | 9.2s | v1 96.714% / v3-rules 96.714% |
| `comparison:rag_multiturn`（120 行） | 9.5s | v1 37.500% / v3-rules 100.000% |
| `load_test`（mock 臂） | 44.4s | P95 160ms / RPS 144.8 / http 错误率 0 / 任务成功率 100% |

锚点：`tag=v0.7.0`、`commit=d7fe209`、`spec_version=1.3`、`dirty=false`。

两个刻意的约束：

- **脏工作区拒绝冻结**（`git status --porcelain` 非空就退出 2）。指标锚不住版本号，
  后面的对比全是幻觉。要放行得显式 `--allow-dirty`，而 `dirty=true` 会写进索引。
- **先写临时目录、全部跑完再搬过去**。否则冻结到一半失败会留下一个半成品
  `releases/<tag>/`，而它看起来像一份完整的基线。

### 12.2 门禁：两条判据，缺一不可

```powershell
D:\Python\python.exe scripts/regression_gate.py --candidate .release-candidate --baseline releases/v0.7.0
```

8 项指标，6 项强制阻断：

| 指标 | 方向 | 绝对下限/上限 | 允许相对基线退化 | 强制 |
| --- | --- | --- | --- | --- |
| `pytest.failed` | 越小越好 | 0 | 0 | 是 |
| `fault.pass_rate` | 越大越好 | ≥ 100% | 0 | 是 |
| `matrix.v3_rules.pass_rate` | 越大越好 | ≥ 90% | 1 个百分点 | 是 |
| `rag_multiturn.v3_rules.pass_rate` | 越大越好 | ≥ 90% | 1 个百分点 | 是 |
| `perf.http_error_rate` | 越小越好 | ≤ 1% | 0.5 个百分点 | 是 |
| `perf.task_success_rate` | 越大越好 | ≥ 99% | 0.5 个百分点 | 是 |
| `perf.p95_ms` | 越小越好 | 无 | 相对 50% | **否** |
| `perf.cost_per_success_cny` | 越小越好 | 无 | 相对 50% | **否** |

- **绝对下限**防的是「基线烂，于是烂变成了标准」：它不管基线多低，指标本身不该跌破线。
- **相对退化**防的是「从 100% 掉到 91%，但没跌破绝对下限」。
- 判定顺序是**先绝对下限、再相对退化**：反过来会先报「比基线掉了多少」，而那个数字在
  指标本身就不可接受时会分散注意力。

两条建议性规则的量纲是**相对**（50%），其余是**绝对**（百分点）。这不是风格差异：
同一份配置的 P95 单次运行能差 2.2 倍（§11.2），给它写死一个毫秒数的容忍度，
做出来的就是随机门禁。**还没压出方差就拿来拦版本，拦的是噪声。**

### 12.3 门禁真的会拦：一次注入回归的实测

只证明「门禁会对」是不够的——一个永远放行的脚本也叫「通过」。所以注入一次真实回归：
把 `RefundTool.refundable_statuses` 从 `{"delivered"}` 改成 `set()`。这很像一次
「手滑收紧了规则」的改动，改完之后冻结候选、跑门禁：

```
  [失败] pytest                          36.9s  1010 passed / 51 failed
  [失败] faults                           4.9s  23/25 条故障用例
  [通过] comparison:matrix                6.2s  213 行
  [通过] comparison:rag_multiturn         5.4s  120 行
```

```
阻断: pytest.failed: 51 > 绝对上限 0
阻断: fault.pass_rate: 92.000% < 绝对下限 100.000%
阻断: matrix.v3_rules.pass_rate: 86.854% < 绝对下限 90.000%
阻断: rag_multiturn.v3_rules.pass_rate: 比基线退化 6.667% > 容忍 1.000%
```

四点值得记下来：

1. **两条判据各自都触发过**：前三条是绝对下限，第四条是相对退化。只写一条的表会在这次
   注入里漏掉一半。
2. **`rag_multiturn.v3_rules` 从 100% 掉到 93.3%**——单看数字仍然是「93 分，挺好」。
   只有和基线比，才看得出它是从满分掉下来的。
3. **日志里有两个「通过」，含义不同，别混。** 冻结输出里的 `[通过] comparison:matrix`
   说的是**这项检查跑成功了**（子进程退出码 0）；分数合不合格是门禁的判定，同一份候选里
   `matrix.v3_rules.pass_rate` 就报了阻断。冻结器只负责「测出来、记下来」，判「好不好」
   是门禁的事——两层分开，才换得来「门禁的判据只有一处定义」。
4. **演示做完立刻 `git checkout --` 还原**，并确认 `git status` 干净。注入回归这件事本身
   也要可回退，否则下一次冻结就带着它一起入库了。

### 12.4 CI：M5 当时三个 job，只有两个阻塞

> 这是 M5 的现场记录。M9 后来加了 `judge-l5` 与 `judge-real`，现在是五个 job（§18.4）。

`.github/workflows/regression.yml`：

| job | 触发 | 干什么 | 阻塞合并 |
| --- | --- | --- | --- |
| `test` | push / PR / 手动 / 定时 | `python -m pytest -q` | 是 |
| `gate` | 同上（`needs: test`） | `freeze_release.py --gate-against releases/v0.7.0` | 是 |
| `nightly-real` | **只在 `schedule`** | 真实模型四方对比 + 真实并发压测（花钱） | 否 |

`nightly-real` 不阻塞有两重结构保证：它在 PR 上根本不触发（`if: github.event_name ==

### 12.5 这一节还没证明的事

1. **这份 workflow 没有在 GitHub 上跑过。** 本机没有 Docker、没有 `gh`，`.github/` 从未被
   GitHub 读过。做过的是：每条 `run` 命令在本机按同一顺序跑过一遍，YAML 能被

2. **`nightly-real` 一次都没触发过**：真实模型的延迟、吞吐与账单仍然是空白（§11.4）。
3. **基线还不够多**。M6 结束时有两份冻结发布（`v0.7.0` / `v0.8.0`，见 §14.5），但

4. **`--skip-load` 会让 `perf.*` 变成「跳过」而不是「失败」**，门禁据此降级为提醒。
   这个区分是必须的（否则快速门禁永远红），但代价是：**跳过压测的候选，不会有任何性能
   证据被检查**。报告里 `skipped_checks` 字段会把它写出来。

## 13. 证据九：M6 方差测量（`--repeat N`）

§11.2 留下的问题是：同一份配置在本机跑了三次，RPS 差 1.7 倍、P95 差 2.2 倍，代码一个字
都没改。M6 给压测脚本加了 `--repeat N`，并把「重复能压掉多少噪声、压不掉多少」量了出来。

### 13.1 `--repeat N` 到底做了什么

不是把同一次运行的数字抄 N 遍。每一次重复都会**重启服务**（新进程、新端口、重新导入代码），
所以它量的是 CI 门禁真正会面对的那种方差，而不是理想条件下的重复精度：

```powershell
# 5 次背靠背，每次 15s，每次重启服务
D:\Python\python.exe scripts/load_test.py --arm rules --users 20 --spawn-rate 5 --run-time 15s --repeat 5 --report reports/variance-rules-15s-5x.json
```

汇总口径写死在报告里（`aggregate_policy` 字段），不是随手取平均：

| 指标 | 口径 | 为什么 |
| --- | --- | --- |
| 延迟 / RPS / 请求数 / token / 成本 | **中位数** | 一次运行的数字本身就是抽样，中位数抗离群 |
| `http_error_rate` | **max**（最坏值） | 「三次里一次 5% 错误率、两次 0%」取中位数是 0%——一次真实故障被平均掉了 |
| `task_success_rate` | **min**（最坏值） | 同上 |

汇总之后**门禁必须重算**。否则会出现「报告正文写着 5% 错误率、门禁那行写着通过」这种
自相矛盾——因为顶层错误率被改写成了最坏值，而门禁还在用某一次运行的结论。
`tests/test_load_test_repeat.py` 里有测试专门钉这两件事（错误率取最坏值、门禁重算）。

`scripts/freeze_release.py --repeat N` 把同样的重复透传给压测，并把 `variance` 写进
`releases/<tag>/release.json` 的顶层；`scripts/regression_gate.py` 再从候选发布里读出来，
印成报告里的「噪声」列（见 13.5）。

### 13.2 背靠背跑 5 次：规则臂（和 §11.2 是同一份配置）

`--arm rules --users 20 --spawn-rate 5 --run-time 15s`，5 次连续跑完（约 95 秒内），
报告在 `reports/variance-rules-15s-5x.json`：

| 指标 | 5 次的值 | 中位数 | 极差 | 相对极差 |
| --- | --- | --- | --- | --- |
| `rps` | 208.3 / 222.3 / 203.8 / 218.7 / 208.1 | 208.3 | 18.5 | **8.9%** |
| `p50_ms` | 84 / 83 / 90 / 83 / 86 | 84 | 7 | 8.3% |

### 13.4 三个结论

**结论一：§11.2 的 2.2 倍不是「重复精度差」，是跨会话漂移。** 那三次是在不同时间点测的，
中间隔着别的进程、别的机器状态。同一份命令背靠背跑 5 次，P95 的相对极差是 25%、RPS 是
8.9%。**所以 `--repeat N` 压的是会话内噪声，压不掉会话间漂移。** 版本对比的正确姿势因此
是两条同时成立：在**同一个会话里**重复，并且让两个版本**在同一个会话里交替**跑——只满足
一条都不够。§11.2 那张表要连同这句话一起读，不要单独引用那几个数字。

**结论二：P95 比 P99 稳得多，门禁该盯 P95。** 规则臂 P95 相对极差 25%、模型臂 4.0%；
而模型臂 P99 的相对极差是 118.9%——5 次里出现了一个 780ms 的离群点（中位数 370ms），
一次 GC、一次系统调度就能把 P99 抬一倍。**N=5 的 P99 不适合当判据**，所以 `RULES` 里只有
`perf.p95_ms`、没有 P99。

**结论三：通过 / 失败类指标是完全确定的。** 5 次里 `http_error_rate` 全是 0%、
`task_success_rate` 全是 100%、`tokens_per_request` 恒为 290、`cost_per_success_cny` 恒为
0.00076——极差都是 0。这不算巧合：mock 臂的 token 是固定估计值，服务端的业务判定是确定性
规则。**真正会飘的只有延迟和吞吐**，而这两个恰好就是门禁里 `enforce=False`（只报警、不拦截）
的两个指标。这个安排现在有了实测依据，不再只是「怕误拦」。

### 13.5 门禁的容差不是拍脑袋定的

`perf.p95_ms` 与 `perf.cost_per_success_cny` 的容差是 `relative 0.50`（改动超过 50% 才拦）。
背靠背实测的会话内 P95 噪声上界是 **25%**（规则臂最坏的一次）。容差 50% ≈ 观测噪声上界的
两倍，留了一倍余量：**能拦住「翻倍级退化」，拦不住「20% 级的慢漂」**——而后者本来就低于
噪声，拦了也只是假警报，还会教人忽略这个告警。

报告里新增的「噪声」列就是为此存在的：`regression_gate.py` 从候选版本的 `release.json`
里读出压测极差，直接印在对应指标旁边。看报告的人不必自己去对照，就知道「这 12% 的退化，
比噪声还小」。

### 13.6 这一节还没证明的事

1. **真实模型的方差仍然是空白。** 上面两组数字全是 mock 臂（`provenance` 里写明
   `latency=modeled` / `tokens=modeled`）。真实 DeepSeek 的延迟漂移、限流，以及**通过率
   方差**，只有 `load_test.py --real --yes --budget` 和 `compare_versions.py --llm --repeat N`
   能测，而它们会花钱。
2. **N=5 只够给出「噪声上界」，不够给出置信区间。** 这里报的是极差而不是标准差，而极差对
   N 敏感（N 越大极差只会越大）。要把 25% 说成「典型噪声」需要 N≥20，代价是 20 倍机时。
   报告里同时留了 `stdev`，但目前没人用它下结论。
3. **压测机与被测服务仍在同一台机器上抢 CPU**（§11.2），所以这些数字里含客户端自己的调度
   开销。绝对值和相对噪声都受影响，并发越高、服务越慢，客户端占比越低。

## 14. 证据十：M6 的通过率方差，以及一个真实的预算熔断 bug

§13 量的是**压测指标**（延迟、吞吐、成本）的方差。M6 的另一半是**判分通过率**的方差：
`compare_versions.py --repeat N`。道理一模一样——同一份用例、同一个版本，跑两次的分数不一样，
这个差值必须和「版本退化」分开，否则门禁拦的是噪声。

### 14.1 口径（写死在报告里，不是随手取平均）

| 指标 | 口径 | 为什么 |
| --- | --- | --- |
| 行级 / 用例级通过率、成本、tokens、模型调用、平均延迟 | **中位数** | 单次运行的通过率是抽样的 |
| `--budget` | **N 次合计**上限 | 每次各自给一份预算 = N 倍预算 |
| 明细（`rows`、未中项） | **离中位数最近的那一次** | 编一份「平均出来的明细」就是造假 |
| `runs[]` / `variance` | 每次的原始数字 + 极差 | 中位数只有配上极差才能读 |

`interpretable_deltas` 给每一对列算一句「这个差值能不能解释」：判据是
`|差值| > max(两边的极差)`（`scripts/variance.py`），故意保守——它默认的答案必须是
「不显著」，否则它就成了把噪声写成结论的帮凶。

### 14.2 全量矩阵跑 5 次：规则列零噪声

`reports/m6-repeat-offline-5x.json`：213 行 × 2 列 × 5 次，全程离线，**总耗时 12 秒**。

| 列 | 行级中位数 | 极差 | 相对极差 | 用例级中位数 | 墙头草用例 |
| --- | --- | --- | --- | --- | --- |
| `v1` | 96.7% | 0.0% | 0.0% | 96.7% | 0 |
| `v3-rules` | 96.7% | 0.0% | 0.0% | 96.7% | 0 |

这个「0.0%」本身就是一条判据：**规则列是确定性的，任何一次在规则列上抖动的结果都一定是
环境或编排的问题，不可能是模型的随机性**。门禁给 `matrix.v3_rules.pass_rate` 的 1 个百分点容差
（213 行里约 2 行）在规则列上非常宽裕；反过来看，模型列的容差该定多少，现在**还没有数据**——那
需要真实调用（14.4）。

### 14.3 一个真实的 bug：`--budget` 被兜底路径吞掉了

写 `--repeat` 的测试时，需要让预算**故意熔断**一次，用的是 `--budget 1e-9`。结果是这样：

```
第 1/3 次: v1 100.0% v2 100.0% v3 100.0% v3-rules 100.0%
```

第一轮**正常跑完**了：6 次模型调用、`plan_source` 全部是 `llm-fallback`、花费
**CNY 0.001246**——比上限高了 **1000 倍**，而这一次运行看起来完全成功。

根因不复杂：`MeteredLLMClient` 每次调用都是「先记账、再 `assert_within_budget()`」，
所以账是记下来的；但 `BudgetExceededError` 是 `LLMError` 的子类，而
`LLMPlanner.plan` 里写的是

```python
except LLMError as exc:
    return self._fallback(message, f"模型调用失败（{type(exc).__name__}）")
```

于是「预算熔断」被当成「模型抽风」处理，降级到规则臂继续跑下一条用例，而**下一条照样超预算**。
6 条用例全部如此：通过率好看、成本爆表、报告里没有任何一条告警。

修法是 planner 里加一个分支（`src/agentevalops/planner.py`）：

```python
except BudgetExceededError:
    raise          # 熔断不是「模型抽风」：降级重试只会继续花钱
except LLMError as exc:
    return self._fallback(...)
```

配一条测试 `tests/test_planner.py::test_llm_planner_does_not_swallow_a_budget_breaker`，
把这个分支钉住。

**为什么之前没人发现**：原来的预算测试全都停在**账本**那一层
（`test_costing.py::test_metered_client_stops_the_run_when_over_budget`），而账本确实会抛。
**没有人验证这个异常能不能穿过规划器**——中间隔着一层 `except LLMError`，异常就消失了。
这一条能进简历里那句「把失败案例定位到检索、推理、工具或状态管理环节」，因为它就是
「模型层的问题被编排层的兜底掩盖掉」的实例。

### 14.4 真实模型的通过率方差：CNY 0.0893 买来的数字

```powershell
D:\Python\python.exe scripts/compare_versions.py --llm --yes --repeat 3 --cases reports/cases-variance-40.jsonl --budget 0.5 --out reports/variance-real-3x.json
```

**用例切片不是随便取的。** `--limit 40` 取的是主矩阵的**前 40 行**，而那 40 行全是
`category=normal`（24 查单 / 10 退款 / 6 转人工）——在这种用例上「模型跑三次分数一样」几乎
是必然，量出来的方差没有意义。所以改成**每个类别各取 10 行**（`normal` / `boundary` / `error` /
`safety`，共 40 行，按文件顺序），把预算花在真正会摇摆的那一段上。

实测（`deepseek-flash`，240 次调用，**4 分 6 秒**跑完，`--budget 0.5` 没用上）：

| 列 | 第 1 次 | 第 2 次 | 第 3 次 | 中位数 | 极差 | 相对极差 |
| --- | --- | --- | --- | --- | --- | --- |
| `v1`（规则） | 92.5% | 92.5% | 92.5% | 92.5% | 0 | 0.0% |
| `v2`（真模型） | 100.0% | 100.0% | 100.0% | 100.0% | 0 | 0.0% |
| `v3`（真模型 + 检索 + 多轮） | 97.5% | 97.5% | **95.0%** | 97.5% | **2.5** | **2.6%** |
| `v3-rules`（规则） | 92.5% | 92.5% | 92.5% | 92.5% | 0 | 0.0% |

每轮花费：`v2` CNY 0.0136、`v3` CNY 0.0163；三轮合计 **CNY 0.0893**——是花费上界
（0.266）的三分之一。token 也在抖：`v3` 三轮分别是 9573 / 9627 / 9454（±0.9%）。

三条结论：

1. **门禁给通过率的 1 个百分点容差，只对规则列成立。** 规则列三次一模一样（极差 0），
   而真模型列 `v3` 的噪声是 **2.5 个百分点**。`interpretable_deltas` 的判断也对得上：
   `v2:v3` 那 2.5% 的差值**正好等于噪声**，被标成「不可解释（低于噪声）」。
   现在 `RULES` 里只检查规则列（`matrix.v3_rules` / `rag_multiturn.v3_rules`），所以 1 个百分点
   没问题；**但哪天要把模型列纳入门禁，容差必须先放到 ≥2.5pp**，否则门禁就是一台噪声报警器。
2. **一条用例就能解释那 2.5pp 的全部波动。** 墙头草用例只有 1 条：`v2_err_validation_01`，
   在 `v3` 上 3 次里过 2 次。这正是 `--repeat` 要抓的东西——**单跑一次时，它那次随机的通过
   会被写进「版本对比」的结论里。**
3. **谁在飘，是可以定位的**：同一次运行里 `v3` 掉 2.5pp，而 `v3-rules` 纹丝不动 → 波动来自
   模型，不来自编排或检索。

**顺带一个只有把真实数字摆在一起才会露出来的接线 bug**：`model_calls` 与 `avg_latency_ms`
挂在**列载荷**上，而 `_column_metric` 是从 `metrics` 里读的——读错位置不会报错，只会让这两项
**静默消失**在 `runs[]` 与 `variance` 里（`summarize_runs` 会把 None 跳过）。报告正文印着
「模型调用 37」，`runs[]` 里却是空的。已修（`PAYLOAD_LEVEL_METRICS`），并加了测试钉住。

## 15. 证据十一：补冻 v0.6.0 —— 三个版本的回归对比

简历上写「3 个版本回归对比」，需要有东西能指过去。原来 `releases/` 里只有两份冻结产物
（`v0.7.0` / `v0.8.0`）——`v0.6.0` 有 tag、没有冻结目录，三版对比缺一角。

这一节把它补齐。**全程离线、零成本、单次 86 秒**，产出两个东西：`releases/v0.6.0/`

### 15.1 为什么 v0.6.0 要单独补冻

冻结器 `scripts/freeze_release.py` 是 M5 才写出来的，`v0.6.0`（M4）冻结时它还不存在。
所以 v0.6.0 是「有 tag、没有冻结目录」。

补冻的麻烦在于：**不能在 HEAD 上跑冻结器**，那样量到的是 HEAD 的代码。做法是开一个
detached worktree 停在旧 tag 上，把量具借过去：

```
git worktree add --detach .worktrees/v0.6.0 v0.6.0
```

借的只有 `scripts/freeze_release.py` 和 `scripts/regression_gate.py` 两个脚本。选它们的
理由很具体：**只用标准库、不 import 本仓库任何模块**——借过去不会把新代码混进旧版本的
测量链路。这一份「量具」提交在 `freeze/v0.6.0` 分支上（`c61d0b3`），worktree 里的
`git describe` 因此变成 `v0.6.0-1-gc61d0b3`。

**这是已知的口径偏差，不是 bug。** `releases/v0.6.0/release.json` 里的 `commit` 记的是
量具提交 `c61d0b3`，不是 tag `v0.6.0` 指向的 `1fd5135`；冻结目录自己的 `README.md`
第一行也把这串 `describe` 原样写出来了。被测代码一个字没动。

### 15.2 两个必须先解决的操作细节

**（a）`PYTHONPATH` 必须指向 `<worktree>\src`。** 本项目是编辑安装（editable install），
`src/` 的路径被钉死在主仓库上。不设 `PYTHONPATH` 就跑，量到的是 **HEAD 的代码**，
而脚本以为自己量的是 v0.6.0——这是「静默量错对象」，比报错危险得多。本机实测踩到过一次。

**（b）用例集必须先核 hash。** v0.6.0 与 HEAD 的四份用例集逐字节相同：

| 用例文件 | 条数 |

| `multiturn_cases.jsonl` | 36 |
| `fault_cases.jsonl` | 25 |

### 15.6 三条诚实警告

**① 功能指标三版一模一样。** `matrix.v3_rules` 三版都是 96.714%、`rag_multiturn.v3_rules`

（同 hash、同口径、锚定齐全），但**区分度低**——它证明的是「流程跑得通、指标没退化」，

`pytest --collect-only` 报 1035 / 1133——差额是 10 个 strict `xfail` 用例：被收集到、但不执行。
同一处论证里只用一种口径。

### 16.7 「零行为改变」与 M8 修掉的 5 个真 bug

插桩最大的风险不是记错，而是**把被测系统改掉了**。防线是
`tests/test_tracing.py::test_instrumentation_does_not_change_behaviour`：同一句话分别用
「带 tracer」和「不带 tracer」的 Agent 跑一遍，审计记录的每个字段必须相同。没有 tracer 时
插桩点 yield 一个 `_NullSpan`（`set` / `fail` 全是空操作），业务代码里**不允许**出现
「有这个 tracer / 没有 tracer」的分支。做不到这一点，「加了可观测性」就变成「换了一个被测
系统」，M3 之前所有回归数字都要重跑。

M8 在写 trace 的过程中修掉 5 个真 bug（都写进 `docs/tracing.md` §8，也都有测试钉住）：

| bug | 为什么危险 |
| --- | --- |
| `prompt_tokens` 被脱敏成 `***` | 键名带 "token" 就替换，**静默删掉了成本指标**。现在有白名单：「带计数提示词的 `*_tokens` 不算凭据」 |
| 发送失败状态被 dump 改写成 `dry-run:` | `error:RuntimeError` 被随后的 dump 覆盖，调用方再也看不到「真发失败」 |
| 显式错误码被异常类名盖掉 | `BUDGET_EXCEEDED` 被 `BudgetExceededError` 覆盖，预算熔断被记成「模型抽风」 |
| 故障注入包在工具外面 → 检索 span 缺失 | 「检索工具超时」那一轮的 trace 里没有任何检索 span，最该看的轮次反而什么都没有。现在检索 span 建在节点里 |
| 视图不渲染用户文本 | 第一版只画 span 名字，XSS 转义测试「通过」是因为页面里根本没有用户文本 —— 同时也说明它把最该看的藏起来了 |

两条与「假通过」有关：**「通过」的测试可能什么都没测**（第 5 条），而**「失败」的状态码
可能不是失败**（§16.6）。这两个坑的方向相反，但都得靠人先想到才测得出来。

### 17.3 L4 与 L3 独立指向同一条 bad case

两套独立实现、不同指标定义，指向同一条用例——这比任何单层分数都更可信。

### 17.4 L5：46 条安全用例全过，且不花钱

每条用例 6 个断言：`is-json` + 状态/错误码逐字比对 + 4 个泄露标记 `not-contains`。

### 18.3 人工抽检：20 / 20，一致率 95%，kappa 0.875

已从真实报告抽 **20 条**：15 条机器失败 + 5 条机器通过（保留 1/4 通过样本，否则测不出假通过）。

### 18.4 CI：五个 job，两个阻塞

| job | 触发 | 跑什么 | 费用 | 阻塞合并 |
| --- | --- | --- | --- | --- |
| `test` | push / PR / 手动 / 定时 | `pytest -q` | 0 | 是 |
| `gate` | push / PR（`needs: test`） | 冻结候选（含 trace；PR 跳过付费判分）+ 原回归门禁 | 0 | 是 |
| `judge-l5` | push / PR / 手动 / 定时（`needs: test`） | Promptfoo 46 条安全用例 | 0 | 是 |
| `nightly-real` | 定时 | 真实模型对比 + 真实压测 | 有上限 | 否 |
| `judge-real` | 定时 / 手动（PR 不触发） | L3 / L4 各 `--repeat 2` + `judge_gate.py` | 上限 CNY 1.9/晚 | 否 |

- L5 是确定性的、零模型费用，所以放在每次 PR 上阻塞。
- L3/L4 每次约 CNY 0.85（2 轮）+ 20 分钟，且需要 `DEEPSEEK_API_KEY` secret，所以只在
  夜间/手动跑；退化会让夜间运行变红，但不挡 PR。
- 门禁基线是提交进 git 的 `quality/judge_baseline.json`，判据有三条：绝对下限、
  比基线低超过容忍值、任何框架错误行。重复报告同时判 `pass_rate` 中位数与 `worst_pass_rate`。
- 本机自检：**9 过 / 0 失败 / 0 跳过**（`reports/judge-gate.md`）。
- 正式冻结时，`freeze_release.py` 默认跑七项检查：原五项 + `trace` + `judge`。
  `trace/` 下是 310 条 trace、失败环节定位和 HTML 视图；`judge/` 下是 L3/L4/L5 报告、
  门禁基线、人工抽检摘要。PR 的 `gate` 用 `--skip-judge`，因为付费报告不在 PR 上生成。

```powershell
D:\Python\python.exe scripts\judge_gate.py --l3 reports/l3-ragas.json --l4 reports/l4-deepeval.json --l5 reports/l5-promptfoo.json
D:\Python\python.exe scripts\judge_gate.py --l3 reports/l3-ragas.json --l4 reports/l4-deepeval.json --l5 reports/l5-promptfoo.json --baseline quality/judge_baseline.json --write-baseline quality/judge_baseline.json
```
